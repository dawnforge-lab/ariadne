# Phase 9: Schema Truth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Pay the three schema debts the Phase 8 gate ledgered (one migration: group-lateral functional indexes, a render-selection column, a collapsed-marker column), wake `structure.deep-page` from two audits of silence by pointing it at `click_depth`, and put `pagesScanned` on `crawl_status` so the audit skill's `crawl.rulesRun` contract loses its three defensive caveats.

**Architecture:** Migration 0012 is the phase's single schema event and lands first; everything else reads what it created. `structure.deep-page` converts from a page rule to a query rule because `click_depth` is written by a derivation that runs *after* the page cursor. `pagesScanned` is derived at read time, not stored — it is exactly `count(*)` of the crawl's pages rows, and the config doctrine forbids a column for a derivable value.

**Tech Stack:** TypeScript strict/ESM, drizzle-kit migrations, Postgres 16, vitest.

**Spec:** No separate spec. The binding record is `docs/gates/phase-8.md` §15 ("Carried into Phase 9" items 1 and 6, "The Phase 9 migration ledger" — all three rows) plus the ledgered doctrine docblocks in `src/crawl/loop.ts` (`storableConfig`/`parseStoredConfig`) and `src/crawl/render/run-render.ts` (`RENDER_URLS_KEY`). Conflicts resolve against those texts.

**Owner decision (2026-08-29):** scope is items 1–3 ONLY of the proposed Phase 9 — the migration trio, the deep-page fix, `pagesScanned`. Thin-floor calibration and the two coverage fixtures (`content.csr-dependent` firing site, no-sitemap site) wait for Phase 10 by the owner's word. Gate is fixture-based; **no client-site crawl this phase**.

**Steps:**

- [ ] **Step 1: schema.ts — the two columns.** On `crawls`:
  ```ts

  // explicit pass was requested — automatic selection, or no render at all;
  // render_pass_count says whether A pass ran, this says who chose the pages.
  // Until migration 0012 this lived under RENDER_URLS_KEY in config_jsonb
  ```

- [ ] **Step 2: schema.ts — the three indexes**, beside the simhash-band precedent, with a comment carrying the measured motivation (10.4 ms/group at 20k pages, gate doc §15) and the parse-tree-match warning the simhash comment already models:
  ```ts

    .on(t.crawlId, sql`btrim(${t.title})`, t.url)
    .where(sql`${t.fetchClass} = 'ok' and ${t.statusCode} = 200 and ${t.isIndexable} = true and ${t.title} is not null`),
  index("pages_dupe_meta_description")
    .on(t.crawlId, sql`btrim(${t.metaDescription})`, t.url)
    .where(sql`${t.fetchClass} = 'ok' and ${t.statusCode} = 200 and ${t.isIndexable} = true and ${t.metaDescription} is not null`),
  index("pages_dupe_h1_text")
    .on(t.crawlId, sql`btrim(${t.h1Text})`, t.url)
    .where(sql`${t.fetchClass} = 'ok' and ${t.statusCode} = 200 and ${t.isIndexable} = true and ${t.h1Text} is not null`),
  ```
  The predicate mirrors `INDEXABLE` in `src/rules/query/field-duplicates.ts:98` **verbatim** (`fetch_class = 'ok' and status_code = 200 and is_indexable = true`) — the planner uses a partial index only when the query's predicate implies the index's, so cross-reference both files' comments at each other.
