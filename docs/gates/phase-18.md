## 1. `crawls.failure_reason` (migration 0017)

Every `failed` close writes its reason; nothing else writes the column:

- the crawl loop's catch (`src/crawl/loop.ts`, `execute`): the first line of
  the error, via the exported `failureReasonOf` — which the API queue runner
  imports rather than re-implementing, and which names the defect ("the crawl
  threw a Error with no message") when the error carries none, because it runs
  inside the recovery path and a throw there would leave the row `running`;
- the robots-unreachable close: the note the loop already composed for
  `CrawlSummary.note` and used to drop;
- the API queue runner's catch (`src/api/service.ts`): the same helper, on the
  throws that never reached the loop;
- the operator's mark-failed call: the exported constant
  `MARKED_FAILED_REASON`.

`closeCrawl` throws both ways — a `failed` close without a reason, a non-failed
close with one — and a successful close writes `null`. Both resume writers
clear it on the way IN as well (`resumeCrawl` in the crawl loop and in
`ApiService`), so a crawl that is `queued` or `running` never carries the last
run's death notice. Contract, stated on the column and
asserted as SQL in `test/db/migration-0017.test.ts`: `failure_reason IS NOT
NULL ⟹ status = 'failed'`; a `failed` row with a null reason is pre-0017.

Served as `CrawlDetail.failureReason: string | null` (not on the listing row),
named in the MCP `crawl_status` description and the `ariadne-crawl` fence, and
documented in `docs/talos-surface.md` §4.2, §5.6 (null-versus-zero) and §9
(posture: a diagnostic string like `renderError` — first line, no stack; an
error from below the loop can carry a host:port or an absolute server path,
which is why it is documented as diagnostic rather than client copy).

The demo page: on `status === "failed"` the progress panel shows "the crawl
failed" with the sentence, or exactly "the engine recorded no reason — a crawl
closed before migration 0017" when the column is null. No rules step follows.

## 2. `sendCsv` and the client that leaves (`src/api/http.ts`)

The pre-existing wedge (`docs/gates/phase-15.md` §7): `once(res, "drain")`
never settles when the socket goes away, because that emits `close`, not
`drain` or `error`. `drainOrGone(res)` settles on drain OR close/error, returns
`false` at once if the response is already destroyed or ended, and removes all
three listeners on every settle (one call per stalled record on a long
export). On gone, `sendCsv` returns out of the `for await` — finalising
`csv.records()`, which releases the reader — destroys the response, and logs
`csv export abandoned by the client <id> <view> after N records, M backpressure
waits`. The wait count is what tells the two endings apart — a client that left
between records (M = 0) from one that left inside the wedge's own branch — and
the test asserts M ≥ 1. The mid-stream-failure catch is unchanged.

One correction to the Phase 15 ledger, recorded in the test's docblock: a
client hitting the API directly never hung `close()` — its own RST freed the
socket; only the demo proxy's shape did. The proxy's upstream-destroy is still
required (it is what turns a closed tab into the API's client leaving), and
its comment now says so in present tense.

The test seeds a 48 MB export (4.6× the ~10.4 MB this machine's TCP buffers
absorb before `res.write` returns false), reads 64 KB, stops reading, aborts;
against the old wait the export went silent for ever; now the abandonment line
appears, the record count is short of a full export, and `close()` resolves.

## 5. What the machine does NOT cover

- Whether a `failure_reason` from an error below the loop (pg, DNS, or any
  `ENOENT`/`EACCES`/`ENOSPC` from the filesystem, which carries an absolute
  server path in its message) is ever shown to a Talos tenant unsanitised: the
  field is documented as diagnostic — paths included, see `docs/talos-surface.md`
  §9 posture 3 — and sanitising at the writer is a one-line change in
  `failureReasonOf` if the seam needs it.
- The TCP-buffer arithmetic in the drain test is measured on this machine and
  given a 4.6× margin; a machine with larger socket buffers would reach the
  backpressure branch later, not never.
